# 銀座Now 記事ハーベスター

決まった情報源から銀座エリアの記事候補を集め、重複を除き、事実確認できたものをまとめて記事にする。記事の形式・執筆ルールは `../ginza-article-writer/SKILL.md`、情報源の一覧は `../ginza-article-writer/references/source-list.md` を参照。

## クイックスタート

1. **機械的な収集を実行する**: `pnpm harvest scan`
   - すべての情報源の一覧を取得 → 既存記事と重複チェック → `new` の候補は詳細ページも取得 → `tmp/harvest-queue.json` に書き出す。
   - `status` の意味:
     - `new`: 一致なし。`detail`（TITLE / OGIMG / OGDESC / FACTS）付き。
     - `maybe_dup`: 既存記事と一致の可能性あり。`matches` に既存 slug。開いて会場・会期を比べる。
     - `needs_resolve`: Google ニュースのリダイレクトURL。実際の記事URLを探してから `pnpm harvest dedup` で再確認。
   - 取得に失敗した情報源は `errors` に出る。同じコマンドを再実行する（スクリプト内で3回リトライ済み）。
2. **候補を選ぶ**: 下記「対象・対象外」に沿って、銀座エリアの読者価値がある候補を選ぶ。件数の上限は設けない。情報源を出し尽くすか、確認が詰まるまで続ける。
3. **スクリプトが拾えない情報源を補う**: クライアント描画やボット対策で一覧を取れないサイト（松屋銀座、歌舞伎美人、資生堂ギャラリー、有楽町マルイ、ポーラ ミュージアム アネックス、銀座三越、メゾンエルメス、銀座 蔦屋書店）は WebSearch の `site:` 検索で個別ページを探す。X.com は発見用にのみ使う。
4. **重複チェックをまとめて行う**: 事実確認の前に、選んだ候補すべてを一括で照合する（[重複チェック](#重複チェック)）。
5. **事実確認**: `pnpm harvest detail "<url>" ...` で詳細ページを確認し、必要に応じて公式ページ・プレスリリースを探す。会期・時間・会場・住所・料金・予約・画像を一次情報で確定する。
6. **記事を書く**: 確認できた候補と重複マージをまとめて `data/articles.json` に追加する（`ginza-article-writer` の形式）。画像は `pnpm harvest image "<画像URL>" "<slug>"` で保存する。
7. **検証**: `pnpm geocode:events`（会場の座標付与）→ `pnpm validate:articles` → `pnpm test` → `pnpm build`（ビルドはバッチ全体で1回）。

出力が長くなるコマンドはファイルにリダイレクトしてから読む:

```bash
mkdir -p tmp && pnpm -s harvest list all > tmp/harvest_out.txt 2>&1
```

## スクリプト

`scripts/harvest.py`（`pnpm harvest <サブコマンド>`）。情報源ごとの取得上の癖はスクリプト冒頭のコメントにまとめてある。サイトのHTMLが変わって取得が壊れたら、`SOURCES` の該当エントリを直接直す。

- `scan [out.json]` — 全情報源の一覧 → 重複チェック → `new` の詳細取得 → `tmp/harvest-queue.json`。
- `list <情報源|all> [--all]` — 候補の `(タイトル, URL)` 一覧。情報源名: `ginza_official`, `chuo_kanko`, `ginza6_events`, `ginza6_popup`, `hibiya_midtown`, `lumine_yurakucho`, `tif`, `ggg`, `tsukiji`, `prtimes`, `collabocafe`, `enjoytokyo`, `walkerplus`, `gnews`, `ceek`。
  - 既存記事の `sources[].url` / `image.sourceUrl` と一致するURL、除外ログに記録済みのURLは自動でスキップ（`--all` で無効化）。
  - 同じ話題の転載（gnews / ceek）は1行にまとめて `(xN)` を付ける。
  - 犯罪報道と、戸越銀座など他地域の「◯◯銀座」はノイズとして件数だけ表示する。
  - `chuo_kanko`・`collabocafe`・`ceek`・`walkerplus` は銀座エリアのキーワード（銀座・有楽町・日比谷・築地・京橋・歌舞伎座など）を含む行だけ残す。
- `detail <url>...` — 詳細ページの TITLE / OGIMG / OGDESC / FACTS（日付・会場・料金・予約などの行）を表示。ページ内に銀座エリアの地名が一度も出てこない場合は WARNING を出す。
- `dedup "<キーワード|URL>" ...` — 重複チェック（下記）。
- `exclude "<url>" "<理由>" "<メモ>"` — 見送った候補を `references/excluded-candidates.jsonl` に記録。
- `image "<画像URL>" "<slug>"` — `public/images/articles/<slug>.<拡張子>` に保存。拡張子は Content-Type から決める。同じ slug の記事・画像があれば保存を拒否する（上書きしない）。

## 対象・対象外

対象:

- 銀座1〜8丁目、有楽町、日比谷、東銀座・築地、京橋・銀座一丁目で、読者が行ける・使えるもの。
- イベント、展覧会、催事、ポップアップ、コラボカフェ、イルミネーション、公演、ワークショップ、まつり。
- イベント以外の出来事: ニューオープン、閉店、リニューアル、移転、施設の名称変更、歩行者天国などの街の変化、地域の公式なお知らせ。
- 丸の内・日本橋は、銀座から歩いて行ける大型イベントのみ。

対象外:

- 会場が銀座エリアにないもの（全国キャンペーン、戸越銀座など他地域の「◯◯銀座」、日本橋・月島だけのイベント）。
- 商品発売だけのニュースで、銀座の店舗・会場での体験や限定がないもの（例: 銀座ブランドの通販新商品）。
- 東京国際フォーラムの業界向け展示会・学会・企業イベントなど、一般の来場者向けでないもの。
- 館内の小さなキャンペーン（決済サービス、ポイント、抽選）で読者価値が低いもの。
- 犯罪・事故で、閉鎖や通行止めなど来訪者への影響がないもの。
- 既に終了したもの。
- 会期と会場（イベント以外は日付・場所・読者への影響）を確認できないもの。

## 重複チェック

```bash
pnpm -s harvest dedup "<キーワード1>|<URL1>" "<キーワード2>|<URL2>" > tmp/dedup_out.txt 2>&1
```

候補ごとに次を照合する:

1. キーワードが既存記事の `title` / `summary` / `content` に含まれるか（TEXT MATCH）。
2. 長いタイトルから抜いた固有名詞（括弧内の名前、英字、カタカナ）が既存記事のタイトル・slug に含まれるか（KEYWORD MATCH）。
3. URL が既存記事の `sources[].url` / `image.sourceUrl` と一致するか（SOURCE URL MATCH、トラッキング引数・末尾スラッシュは無視）。
4. URL のローマ字部分が既存の slug・画像ファイル名に含まれるか（SLUG/IMAGE TOKEN MATCH）。
5. 除外ログに記録済みか（PREVIOUSLY EXCLUDED）。

一致はあくまで手がかり。既存記事を開いて会場・会期を比べてから判断する。

- 同じイベント → 新規記事は作らず、マージチェックする（下記）。
- 同じシリーズ・同じ会場でも、会期が違えば別の回として新規記事にしてよい。
- 「ミッドタウン」「GINZA SIX」など会場名だけの一致は別イベントのことが多い。
- 既存記事が2本で同じイベントを扱っていたら、古い slug に統合し、新しい方を削除する（画像も `git rm`）。

## マージチェック

重複候補は、既存記事より新しい情報（グッズ・メニュー・料金・予約方法・出演者・会期変更・公式URL）を持っていることが多い。重複と判断した候補も、捨てる前に必ず既存記事と比べる。

- 情報源で確認できた事実だけを `summary` / `content` / `event` に反映する。
- 新しい情報源は `sources` に追加する（URL正規化で重複除去、公式を先に）。gnews のリダイレクトURLは使わず、実際の記事URLを記録する。
- `publishedAt` は更新しない。slug は変えない。
- 本文・開催情報を更新したら `updatedAt` に作業日（YYYY-MM-DD）を入れる（`dateModified` と sitemap の lastmod に反映される）。情報源の追加だけなら変えない。
- 新しい情報がなければ既存記事はそのまま。

## 除外ログ

`references/excluded-candidates.jsonl` には、調べたうえで見送った候補を1行1件で記録する。次回以降の巡回で同じURLを調べ直さないため。

- 形式: `{"url": "...", "reason": "...", "note": "...", "checked": "YYYY-MM-DD"}`
- `reason`: `out_of_scope_area`（銀座エリア外）、`event_ended`（終了済み）、`not_ginza_specific`（全国・他地域向け）、`insufficient_facts`（会期・会場などが確認できない）、`low_value`（対象だが記事にする価値が低い）
- 見送りを決めたらその場で記録する: `pnpm harvest exclude "<url>" "<reason>" "<メモ>"`
- 既存記事と重複していた候補は記録しない（`sources[].url` で次回もスキップされる）。

## 情報源の記録

- 発見に使ったページと確認に使ったページを、すべて `sources` に残す。
- まとめサイト（レッツエンジョイ東京、ウォーカープラス、コラボカフェ、PR TIMES）で見つけた候補は、必ず公式ページを探して先頭に置く。
- 並び順: 公式 → チケット・会場 → プレスリリース → まとめ・発見元。
- ラベル例: `公式サイト`、`GINZA SIX 公式ニュース`、`松屋銀座 公式イベントページ`、`PR TIMES プレスリリース`、`レッツエンジョイ東京 イベントページ`、`コラボカフェ 記事`。

## スクレイピングの委任

候補の詳細取得が多いときは `web-scraper` エージェントにまとめて任せてよい（URL と欲しい項目を明示する）。重複判断・採否・`data/articles.json` の編集・画像配置・検証はメインで行う。

## 報告

作業後の報告は短く:

- `追加`: 作成した slug
- `マージ`: 新しい情報で更新した既存 slug（何を追加したか）
- `統合`: まとめた既存記事（残した slug ← 削除した slug）
- `重複`: マージチェックしたが新情報がなかった slug
- `保留`: 理由（除外ログに記録済み）
- `確認`: `pnpm validate:articles`・`pnpm test`・`pnpm build` の結果
